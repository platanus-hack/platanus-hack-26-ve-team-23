# ADR-0029: Daemon pinning and host enrolment approved by the owner

- **Status:** Proposed
- **Date:** 2026-10-24
- **Deciders:** Javier Hernandez, team-23

## Context

Until now the trust between a host daemon and the Core was one-sided and
on first use:

- The daemon pinned the first active Core it found on the network (or
  `GUARDIAN_CORE_ID`) and wrote its id to `core.pin`. Whoever announced a
  Core first on the LAN got the daemon, and anything on the host that could
  write `core.pin` could repin it.
- The Core decided for **any** authenticated peer. A rogue daemon, a copy of
  a daemon key on another machine, or a fresh key generated by an agent got
  decisions like an enrolled host.

The owner must say which machines a Core serves, and each daemon must obey
one Core only, with a pin that has a format version and survives changes of
Core in a controlled way.

## Options considered

### Option 1: keep trust on first use

- Benefits: zero setup.
- Drawbacks: first-come pinning on the LAN; no list of hosts on the Core.

### Option 2: pin at build time only

- Benefits: nothing on the host can change it.
- Drawbacks: one build per Core; no way to enrol hosts after deployment.

### Option 3: owner approval, with a build-time pin when wanted

The owner approves each host from the app, with a signature over the Core,
the daemon identity, its HWID and the time. The Core serves only approved
hosts; the daemon pins the Core and the owner when it receives the approval.
A build can fix the Core instead.

- Benefits: the owner decides; the approval is bound to one key on one
  machine; works for fleets built once and for hosts added later.
- Drawbacks: one tap per host in the app; an unapproved host is denied.

## Decision

Option 3.

### Key points

- **Pin sources, in order:**
  1. Build: `HAWK_CORE_ID` (and optionally `HAWK_OWNER_PUBLIC`) when the
     daemon is compiled. Fixed.
  2. Environment: `GUARDIAN_CORE_ID`. Fixed for the life of the service.
  3. Enrolment: `core.pin` written when the owner's approval arrives.
  4. None: the daemon talks to one Core for the session and writes nothing.
- **Pin file v2** (`core.pin`, JSON): `v` (format version, 2), `core`,
  `owner`, `epoch`, `source`, `approved_ms`. A v1 file (the bare Core id)
  is still read; an unknown version is ignored, so the daemon is unpinned
  and its calls are denied rather than trusting a file it cannot read.
- **The daemon obeys only its pinned Core.** The TLS handshake refuses any
  other Core key; requests on the connection are answered only if they come
  from that key; an approval is accepted only from the pinned Core and,
  once an owner is pinned, only with that owner's signature.
- **Approval.** `Request::ApproveHost { approval }` from the paired app only.
  `approval` = `{ core, host, hwid, timestamp_ms, signature }`, the owner's
  P-256 signature over `guardian.approve-host.v1 || core || host ||
  len(hwid) || hwid || timestamp_ms`. The Core checks it is for this Core,
  for a connected host reporting that HWID now, at most 60 s old, and signed
  by the paired owner; then keeps it in `approved-hosts.json`, records it,
  and hands it to the daemon (`Request::Enrolled`), again on every hello.
- **The Core decides only for approved hosts** with the HWID they were
  approved with (ADR-0028): every other call is denied (`host not approved
  by the owner`), without recording it, so strangers cannot fill the record.
- **Epoch.** Every enrolment pin starts at epoch 1. Moving hosts to a new
  Core (a new Core key) will be an owner-signed pin with the next epoch,
  relayed by the old Core; an older epoch is never accepted.

## Dependencies and licences

None new. The daemon now uses `p256` and `serde`, already in the workspace
(ADR-0017, MIT OR Apache-2.0).

## Consequences

### Positive

- A daemon cannot be taken over by a Core announced first on the LAN, nor
  repinned by editing a file once it is approved (the owner key is pinned).
- An agent that re-keys the daemon, copies its key elsewhere or runs a
  daemon of its own gets denials, and the owner sees the attempt.

### Tradeoffs

- Every new host needs the owner's tap before it works.
- Before approval the daemon still trusts the first Core it reaches for
  that session; the owner compares the fingerprints (Identify) before
  approving. A build-time pin removes this window.
- Revoking an approval and moving hosts to a new Core are not built yet.

## Implementation

### Where it lives

- `host-daemon/src/pin.rs`: sources, file v2, checking an approval.
- `guardian/src/enrolment.rs`: approvals kept by the Core.
- `guardian/src/api.rs`: `ApproveHost`, the gate in `Decide`, `Enrolled`.
- `guardian-core/src/wire.rs`: `HostApproval`, `approve_message`.
- `witness`: the Approve button and `approve_host`.

### Next steps

1. Revoke an approval from the app (signed), which also contains the host.
2. Pin rotation to a new Core with the next epoch.
3. Attestation (ADR-0021) so the HWID itself is bound to the hardware.
